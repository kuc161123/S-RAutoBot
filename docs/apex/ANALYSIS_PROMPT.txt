4. DESIGN THE ELLIOTT ENGINE AND AI COLLABORATION

Use a reproducible numeric engine for candles, pivots, Fibonacci arithmetic,
wave constraints, levels, price precision and risk calculations. Each pivot must
record occurrence and confirmation time. Each count revision must be stored as
it was known then, with anchors, degree, primary/alternate status, deciding price,
invalidation, evidence and supersession reason. Recounting must not rewrite past
signals or make a backtest see future extrema.

Propose these functional roles, consolidating roles where tests show no benefit:
• Research: fresh sourced market events, funding/positioning and context.
• Wave analyst A and B: separate initial counts from the same frozen data packet,
  without seeing each other's answers during the first pass.
• Critic/validator: challenge structure and cite concrete disagreements.
• Coordinator: reconcile accepted evidence and maintain opportunity state.
• Quant evaluator: score predictions and test candidate improvements offline.
• Reporter: explain decisions in concise Telegram messages from committed state.

Evaluate an AI layer using official OpenAI APIs from the cloud. Production use
must have a defined benefit and be compared with the deterministic baseline;
do not add agents solely to make the architecture look more sophisticated.
Evaluate Responses plus the Agents SDK
against a managed Agents API workflow; select the least complex option that
meets reproducibility, isolation, latency, cost and recovery needs. Do not assume
a desktop chat, this conversation, its agents, credentials or project memory
automatically becomes part of the deployed application. Define versioned prompts,
allowed tools, persisted context and model configuration explicitly.

Require structured outputs linked to supplied candle/pivot IDs and source
timestamps. Validate semantics after schema validation: a schema-valid answer
can still be wrong. Handle refusal, incomplete output, malformed values,
unsupported claims, contradictory counts, model changes, rate limits and timeouts.
Keep identical frozen inputs for independent reviews. Define an abstention and
bounded retry policy; avoid endless agent discussion.

Provide models with read-only scoped research tools and minimum necessary data.
Exchange credentials and raw private account data do not belong in web queries,
prompts or traces. Web content cannot issue instructions. The AI can propose a
trade plan; a separate deterministic policy engine validates it and the execution
service owns exchange actions. AI cannot directly change code, deploy releases,
raise risk limits or override a halted state.

Call expensive reasoning on new closed bars or material structure changes, not
every tick. Give near-zone candidates priority. Specify per-role budgets, caching
keys, maximum concurrency, latency deadlines and cost telemetry. Validate model
availability and current pricing before selecting a production model. Provide
monthly cost scenarios with explicit assumptions, including search and storage.

6. PORTFOLIO POLICY, EXECUTION AND RESTART SAFETY

Extract Apex's tier risk, gross heat, bucket limits, position/notional caps,
isolated leverage/liquidation checks, directional switches, regime/event
multipliers and daily/weekly/drawdown breakers. Contrast them with the current
bot's different policy. Preserve sourced rules as the design baseline; identify
proposed changes explicitly and justify them with tests.

Design an explicit capital policy: distinguish owner-authorized allocation,
exchange equity, available margin and external/OWN positions. Do not turn an old
capital figure into current cash, auto-increase it, or ignore account-wide exposure.
Existing OWN positions must not be managed as bot positions. Prefer separate
execution ownership or a dedicated subaccount in the design; document what
requires one-time provisioning and what can run autonomously thereafter.

Replace routine PLACED/SKIP and ticket checks with a tested order state machine:
candidate -> eligible -> risk reserved -> intent persisted -> submitted ->
acknowledged -> partially filled/filled/rejected/cancelled/unknown -> protected
-> managed -> closed -> reconciled. Persist intent before sending. Use unique,
stable client IDs, reconciliation before retrying ambiguous submissions and
transactional risk reservations so concurrent signals cannot overspend the caps.

Order acceptance is not a fill. Confirm exchange quantities, fill prices, costs
and protection before reporting a position as executed. Handle partial fills,
unfilled expiry, disconnects, protective-order failure, reduce-only exits,
one-way-mode conflicts and delayed/out-of-order events. Never expand a stop to
preserve a wave narrative or re-enter automatically from stale pre-restart signals.

On restart, reconcile orders/positions before new entries, recover entry-risk
metadata, retain pause/halt state and dedup state, and resume scheduled work.
Use a cloud-safe single execution leader with fencing/lease-loss behavior rather
than process-name killing. Treat Postgres failure as an execution incident;
ephemeral JSON is not an authoritative cloud trading ledger.

Periodic status/daily summaries should expose overall health and stale waiting
